# SpecBox Sync: локальный backend для `serve`

## Назначение и границы

Команда `spec-box serve` запускает один локальный Node.js-процесс, который
обслуживает Angular SPA, внутренний JSON API и Server-Sent Events (SSE).
Сервер работает с текущей рабочей копией проекта на диске.

В MVP backend поддерживает:

- просмотр и редактирование исходных YAML-спецификаций;
- создание новых YAML-файлов и нужных для них каталогов;
- валидацию и расчёт покрытия по существующим отчётам Jest и JUnit;
- обновление данных после внешних изменений файлов;
- построение деревьев по `.spec-box-meta.yml` и графа ссылок `$feature-code`;
- просмотр локальной Git-истории и YAML-снимков фичи в прошлых ревизиях.

Backend не запускает тесты, не вызывает `api.host`, не изменяет `.tms.json`,
`.spec-box-meta.yml` или отчёты и не поддерживает совместное редактирование.
Отдельные база данных, очередь и внешний сервер не требуются.

Тело YAML не нормализуется: комментарии, неизвестные поля, порядок ключей и
форматирование сохраняются. `filePath` обязателен только в JSON-запросе
создания новой фичи.

## Запуск и источники данных

`serve` использует тот же конфигурационный файл, каталог проекта, загрузчики
YAML, валидатор и matcher-ы Jest/JUnit, что и существующие команды CLI. Эти
модули остаются единственным источником правил формата, валидации и покрытия.

Сервер слушает только `127.0.0.1` и `::1`. Если порт не указан, его выбирает
ОС, а команда выводит полный URL. При некорректном `.tms.json` при запуске
команда завершается с диагностикой. Если уже запущенный сервер обнаруживает
некорректную новую версию `.tms.json`, он публикует новый снимок только с
ревизией и диагностикой.

## Снимок проекта

Backend хранит в памяти один `ProjectSnapshot`. Он полностью пересчитывается
при запуске, после сохранения и после изменения наблюдаемого файла. В MVP
инкрементальный пересчёт не нужен.

Снимок содержит:

- номер ревизии снимка;
- данные проекта, атрибуты и фичи;
- общий список нормализованных диагностик с типом, важностью, путём и
  описанием ошибки;
- для каждого утверждения `isAutomated` и сводные показатели: всего,
  автоматизировано и без покрытия;
- дерево существующих каталогов для каждой области хранения спецификаций;
- вычисленные деревья фич из `trees[].group-by`;
- граф ссылок между фичами.

Дерево каталогов строится по существующим каталогам в статической части
каждого положительного шаблона `yml.files` до первого сегмента с glob. Если
шаблон начинается с glob, его корнем считается каталог проекта. Отрицательные
шаблоны не создают областей хранения.

Ошибка YAML, мета-файла или отчёта не останавливает сервер: она включается в
диагностики, а данные остальных валидных файлов остаются доступны. Покрытие
означает только сопоставление утверждения с тестом в текущем отчёте;
успешность запуска теста на него не влияет.

## HTTP API

API является внутренним контрактом между SPA и `serve`; его маршруты не
предназначены для внешних клиентов.

| Метод и маршрут | Результат |
| --- | --- |
| `GET /api/project` | Текущий `ProjectSnapshot`. |
| `GET /api/features/:code` | Исходное тело YAML и `ETag` текущего файла. |
| `GET /api/features/:code?revision=:commit` | Исходное тело YAML из указанной Git-ревизии. |
| `POST /api/features` | Создаёт YAML-файл фичи и возвращает новый снимок. |
| `PUT /api/features/:code` | Сохраняет YAML при совпавшем `If-Match` и возвращает новый снимок. |
| `GET /api/features/:code/history` | История Git-файла фичи. |
| `GET /api/events` | SSE-поток обновлений проекта. |

### Содержимое YAML-файла

`GET /api/features/:code` без параметра возвращает неизменённые байты файла с
`Content-Type: application/yaml; charset=utf-8` и `ETag`: MD5 байтов в
кавычках. Параметр `revision` принимает только идентификатор коммита из
истории этой фичи и возвращает YAML из этой ревизии без `ETag`. Если фичи либо
файла в указанной ревизии нет, endpoint возвращает `404`.

История возвращает идентификатор коммита, автора, дату и сообщение. Когда Git
недоступен или файл не отслеживается, она возвращает пустой список с `200`.
Построчный Git diff backend не строит: UI запрашивает два YAML-снимка и
сравнивает их текст.

### Создание фичи

Минимальный запрос `POST /api/features`:

```json
{
  "filePath": "specs/backend/serve.spec.yml",
  "code": "serve",
  "title": "Локальный сервер"
}
```

`filePath` задаётся относительно каталога проекта, включает имя файла и
суффикс. Backend нормализует путь; он не может выйти из каталога проекта,
должен соответствовать хотя бы одному положительному шаблону `yml.files` и
не должен соответствовать исключающему шаблону. Имя и суффикс полностью
задаёт пользователь; сервер ничего к ним не добавляет.

Перед записью сервер проверяет структуру запроса, формат кода, непустое
название, уникальность кода и отсутствие файла по указанному пути. Ошибка
запроса не создаёт ни каталогов, ни файла. При успешном запросе backend
создаёт недостающие родительские каталоги и минимально валидный YAML только в
этот момент. Описание, атрибуты, группы и утверждения добавляются через
последующий `PUT`.

### Редактирование фичи

`PUT /api/features/:code` принимает YAML прямо в теле с
`Content-Type: application/yaml; charset=utf-8`. Клиент передаёт полученный
из `GET` `ETag` в заголовке `If-Match`. Перед записью backend сверяет его с
MD5 текущих байтов файла; при несовпадении он возвращает `409` без тела и не
меняет файл. Проверка best-effort: внешняя запись в микропаузе после сравнения
допустима в MVP.

Backend записывает тело без разбора, преобразования или валидации структуры.
Поэтому комментарии, неизвестные YAML-поля и форматирование не теряются.
Синтаксические и доменные ошибки, включая неразрешённые ссылки и повторные
`assert`, не мешают записи и включаются в диагностики нового снимка.

После `POST` или `PUT` сервер немедленно пересчитывает снимок и возвращает
его вместе с диагностиками.

Отсутствующая фича или ревизия возвращает `404`, отсутствующий либо
несовпавший `If-Match` — `409` без тела.

## Деревья, граф и уведомления

Для каждого правила `trees[].group-by` backend строит дерево фич. Фича
попадает во все ветви комбинаций значений её атрибутов. Если значение
группирующего атрибута не задано, используется ветвь «Не задано».

В графе вершина соответствует фиче, а ребро — ссылке `$feature-code`. Если
целевая фича отсутствует, ребро сохраняется с признаком неразрешённой ссылки,
чтобы UI мог показать его вместе с диагностикой.

Watcher наблюдает за `.tms.json`, мета-файлом, YAML-файлами и каталогами
областей хранения, а также настроенными отчётами Jest/JUnit. Несколько
быстрых событий объединяются в один пересчёт. После каждого пересчёта ревизия
снимка увеличивается, а SSE отправляет событие
`project-updated` с новой ревизией. Получив его, UI заново запрашивает
`GET /api/project`.

## Проверяемые результаты

1. `spec-box serve` открывает UI только на loopback-адресе и не обращается к
   `api.host`.
2. UI получает один снимок с диагностиками, покрытием, деревьями и графом
   для проекта с корректными и ошибочными YAML-файлами.
3. UI создаёт фичу по полному пути, подходящему под `yml.files`; новые папки
   появляются только после успешного `POST`.
4. Некорректный `POST` с неподходящим путём, существующим файлом или
   дублирующим кодом возвращает `400` и не меняет рабочую копию.
5. После `PUT` либо внешнего изменения наблюдаемого файла UI получает
   `project-updated` и видит пересчитанные диагностики и покрытие.
6. UI получает историю отслеживаемой фичи и YAML-снимок любой выбранной
   ревизии; отсутствие Git не мешает просмотру и редактированию.
7. `PUT` с устаревшим `If-Match` возвращает `409` без тела и не меняет
   YAML-файл.
