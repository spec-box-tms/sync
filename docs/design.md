# SpecBox Sync: локальный rich UI

## Цель

Добавить команду `spec-box serve`, которая запускает локальный HTTP-сервер на
свободном порту и предоставляет браузерный интерфейс для просмотра,
редактирования и проверки YAML-спецификаций проекта. В MVP интерфейс работает
только с рабочей копией на диске: он не вызывает `api.host` и не требует сети.

## Границы MVP

В MVP входят:

- просмотр фич, групп утверждений, атрибутов и метаданных проекта;
- создание YAML-фичи по указанному пути;
- редактирование исходного YAML-файла без преобразования его структуры;
- валидация и пересчёт покрытия тестами после сохранения;
- обновление UI при изменениях YAML, мета-файла или отчётов на диске;
- дерево фич по правилам `trees[].group-by` из `.spec-box-meta.yml`;
- граф зависимостей по ссылкам `$feature-code`;
- Git-история YAML-файла и сравнение его содержимого в двух ревизиях;
- просмотр покрытия по существующим отчётам Jest и JUnit.

В MVP не входят запуск тестов, синхронизация с удалённым API, совместное
редактирование, учётные записи и отдельное развёртывание frontend-приложения.

## Архитектура

`serve` запускает один локальный Node.js-процесс, привязанный к loopback
интерфейсу. Он одновременно раздаёт собранную Angular SPA, предоставляет JSON
API и отправляет изменения через Server-Sent Events (SSE).

```text
Browser (Angular SPA)
        | HTTP: read/save/history
        | SSE: project-updated
        v
spec-box serve (local Node.js server)
        |-- configuration and project loader
        |-- validator and Jest/JUnit matchers
        |-- YAML read/write adapter
        |-- file watcher
        |-- local Git adapter
        v
working tree: .tms.json, YAML, .spec-box-meta.yml, test reports, .git
```

Существующие загрузчик конфигурации, загрузчик YAML, доменная модель,
валидатор и сопоставление тестов остаются единым источником правил. Сервер
вызывает их через тонкие адаптеры, а не повторяет правила в HTTP-слое или
Angular-клиенте.

Репозиторий становится монорепозиторием. Angular-исходники и серверный код
развиваются вместе, но публикуемый npm-пакет содержит только CLI, серверный
код и скомпилированный static-дистрибутив Angular. Точная раскладка исходников
и пакетов намеренно не выбрана в этом документе.

## Модель данных и пересчёт снимка

Сервер хранит в памяти один `ProjectSnapshot`:

- данные проекта, фичи, атрибуты и деревья;
- номер ревизии снимка и дерево существующих каталогов областей хранения;
- общий список нормализованных диагностик валидации;
- для каждого утверждения — результат сопоставления с отчётами;
- агрегаты покрытия: всего утверждений, автоматизировано, без покрытия;
- граф ссылок между фичами.

При старте, после сохранения и после файлового изменения сервер заново строит
снимок из файлов. Для MVP полный пересчёт предпочтительнее инкрементального:
он использует уже проверенный поток CLI и исключает рассинхронизацию индексов.

Watcher наблюдает за `.tms.json`, мета-файлом, YAML-файлами и каталогами
областей хранения из `yml.files`, а также настроенными отчётами Jest/JUnit.
Несколько быстрых событий объединяются в один пересчёт. Каждый пересчёт
увеличивает ревизию снимка и публикует SSE-событие `project-updated`; UI
запрашивает новый снимок.

Ошибка чтения или валидации также попадает в общий список диагностик снимка.
Невалидный YAML не мешает работе с другими фичами; при невалидном `.tms.json`
снимок содержит только ревизию и диагностики.

## Локальный API

API является внутренним контрактом между SPA и `serve`; он не публикуется как
внешний сервис.

| Операция | Назначение |
| --- | --- |
| `GET /api/project` | Текущий `ProjectSnapshot`. |
| `GET /api/features/:code` | Исходное тело YAML-файла и его `ETag`. |
| `GET /api/features/:code?revision=:commit` | Тело YAML-файла из указанной Git-ревизии. |
| `POST /api/features` | Создать YAML-файл фичи и вернуть обновлённый снимок. |
| `PUT /api/features/:code` | Сохранить YAML из тела запроса при совпавшем `If-Match`, затем вернуть обновлённый снимок и диагностики. |
| `GET /api/features/:code/history` | Локальный Git-лог YAML-файла. |
| `GET /api/events` | SSE-поток изменений проекта. |

`POST /api/features` принимает `filePath`, `code` и `title`. Путь задаётся
относительно каталога проекта, должен соответствовать положительному шаблону
`yml.files` и не соответствовать исключающему; при успехе сервер создаёт
недостающие родительские каталоги и минимально валидный YAML. Ошибка запроса
не создаёт ни каталогов, ни файла.

`GET /api/features/:code` возвращает неизменённые байты текущего YAML с
`Content-Type: application/yaml; charset=utf-8` и `ETag`, равным MD5 этих
байтов в кавычках. Клиент сохраняет этот заголовок и передаёт его в
`If-Match` при `PUT /api/features/:code`. Тело `PUT` — YAML с тем же
`Content-Type`; сервер записывает его без разбора, нормализации или удаления
комментариев. При несовпадении `If-Match` с текущим `ETag` сервер возвращает
`409` без тела и не меняет файл.

Код, путь и любые YAML-поля редактируются только в YAML. После записи сервер
полностью пересчитывает снимок; ошибки синтаксиса и валидации остаются в его
диагностиках и не отменяют сохранение. Неразрешённые ссылки и повторные
`assert` также сохраняются и попадают в диагностики нового снимка.

Никакая операция UI не меняет `.tms.json`, `.spec-box-meta.yml` или отчёты
тестов.

## Интерфейс

SPA состоит из трёх представлений:

1. **Спецификации.** Слева отображается плоский список фич либо выбранное
   дерево из правил мета-файла. Пользователь может создать фичу, указав путь,
   код и название. Справа — текстовый редактор исходного YAML; при открытии
   он получает содержимое файла и `ETag`, при сохранении отправляет YAML с
   `If-Match`. Диагностики отображаются общим списком проекта, покрытие — в
   модели фичи.
2. **Зависимости.** Ориентированный граф: вершины — фичи, рёбра — ссылки
   `$feature-code`. Из вершины можно открыть фичу в первом представлении.
3. **История.** Для выбранного YAML отображается Git-лог, выбор двух ревизий
   и сравнение двух YAML-снимков. Если файл не отслеживается
   Git или Git отсутствует, показывается пустое состояние, а не ошибка
   приложения.

Редактор не преобразует YAML: комментарии, порядок ключей, неизвестные поля и
исходное форматирование сохраняются, пока их не изменит пользователь.

## Git и покрытие

Git-адаптер использует локальный Git CLI только для чтения истории и
содержимого YAML в ревизиях; UI сравнивает исходный текст YAML.
Ошибки Git не мешают просмотру и редактированию спецификаций.

Покрытие строится существующими matcher-ами по `jest` и `JUnit` из
`.tms.json`. Оно означает «утверждение сопоставлено с тестом в текущем
отчёте», а не запуск или успех теста. UI не запускает тестовую команду;
обновление отчёта на диске инициирует пересчёт.

## Безопасность и отказоустойчивость

- Сервер слушает только `127.0.0.1`/`::1`, не открывая доступ к файловой
  системе сети.
- Все пути проверяются относительно каталога проекта из конфигурации; API не
  принимает произвольные пути к файлам.
- Неудачная загрузка одного файла не завершает сервер: он отдаёт диагностику
  и продолжает наблюдение за изменениями.
- Если свободный порт не задан, сервер выбирает его ОС и выводит точный URL в
  консоль.

## Этапы поставки

1. Выделить общий загрузочный поток из CLI и добавить `serve` с read-only API
   и static Angular shell.
2. Реализовать создание, список, деревья, страницу фичи и сохранение исходного
   YAML с `ETag`/`If-Match`.
3. Подключить watcher, SSE и отображение покрытия из отчётов.
4. Добавить граф зависимостей и Git-историю со сравнением YAML-снимков.

Каждый этап оставляет рабочую локальную команду; отдельный сервер, база данных
или удалённый API для этого не требуются.

## Отложенные решения

- Раскладка monorepo: границы каталогов и пакетов frontend, CLI и общего кода.
- Детальный UX редактора, включая навигацию по большим деревьям и отображение
  конфликтов и точечную привязку диагностик к сущностям формы.
